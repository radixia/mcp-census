# Phase 1 pilot — 2026-08-05

First real measurement. **Not a release**: the sample is a pilot, not a frozen
universe, and no numbers here should be cited as census results.

- **Population:** 501 domains — top 250 global, top 150 European ccTLD, top 100
  `.it`, plus `radixia.ai`. Drawn from Tranco list `Y8VWG`, infrastructure
  domains excluded. Selection rule: `scripts/pilot/sample.ts`.
- **Methodology version:** `0.2.0-draft`
- **Candidate set:** `2026-08-04`
- **Wall clock:** 2358s (39 min) at concurrency 16

## The finding: nobody implements the current proposal

Which candidate path responded, across all `D1` hits:

| Path | Provenance | Hits |
|---|---|---|
| `/.well-known/mcp.json` | **superseded** — original SEP-1649/2127 shape, never accepted | 4 |
| `/.well-known/mcp/server-card.json` | **unattested** — appears in no primary document | 4 |
| `/.well-known/mcp` | **historical** — SEP-1960, never adopted | 1 |
| `/.well-known/ai-catalog.json` | current SEP-2127 direction | **0** |
| `/.well-known/mcp-server` | draft-serra | **0** |
| `_mcp.<apex>` TXT | draft-serra / draft-morrison | **0** |

**Every deployed server card sits on a superseded or unattested path. Not one
domain implements where the specification is actually heading.** The single most
common path, tied at 4 hits, is one that exists in no primary document at all —
it propagated through blog posts. See `docs/SPEC-NOTES.md` §4.

### The documents do not agree either

Among the five cards found, at least four incompatible shapes:

- `cloudflare.com` — `{"mcpServers": {...}}`, which is the **client
  configuration** format, not a server card
- `forter.com` — `$schema: modelcontextprotocol.io/schemas/discovery.json`, a
  schema URL that does not exist
- `sentry.io` — `{name, description, endpoint}` at one path and
  `{name, description, url, provider, authentication}` at the other
- `radixia.ai` — the MCP Registry `server.json` schema

An agent cannot parse this population with one parser. That is the fragmentation
argument, measured rather than asserted.

## Our own row

`radixia.ai` scored **50, Discoverable** — `D1` ✅, `D3` ✅, `F1` ✅, `F2` ✅,
`D4` ❌, `D2` ❌. Three defects, disclosed here because we name other domains:

1. **`D4` fails — the only MUST-level check.** `mcp.radixia.ai` answers
   `/.well-known/oauth-protected-resource` with `200` and a plain-text
   human-readable page instead of RFC 9728 JSON. A `404` would be more correct
   than what we serve.
2. **The MCP host is a `200` catch-all.** Every unmatched path returns a text
   blurb, so automated tooling cannot distinguish "present" from "absent".
3. **Both our cards are on non-current paths**, exactly like everyone else's.

## Bugs this run found

Three, none of which the fixture tests caught, all fixed:

1. `D1`/`D4` resolved endpoint-relative candidates against the apex instead of
   the endpoint's host — a systematic false negative on `D4` for every domain
   with an `mcp.*` subdomain.
2. DNS failures were retried, making a 500-domain run take ~7 hours.
3. An off-apex redirect threw a guard violation and aborted the whole domain,
   losing every check for auth-walled sites such as `office.com`.

## Caveats

- `otomoto.pl` returned `403` to a later manual check having returned `200`
  during the run. Bot mitigation makes some rows time-dependent — Limitation 3,
  now observed rather than hypothesised.
- Three of the seven Discoverable domains (`workbox.dk`, `prodregistryv2.org`,
  and arguably `meraki.com`) are infrastructure or long-tail rather than
  consumer brands.
- `D5`/`D6` are unimplemented, so no domain can exceed 65.
- `.well-known` candidates are probed on the apex only; see Limitation 6.
